Программа моделирует модуль «Учет финансов» для ТигрБанка. Она позволяет пользователям управлять личными финансами: вести счета, категории доходов и расходов, операции. Основные сущности:

BankAccount – счет пользователя (имя, баланс).

Category – категория операции (тип: доход/расход, название).

Operation – финансовая операция (сумма, дата, описание, привязка к счету и категории).

Бизнес-логика включает создание/редактирование/удаление сущностей, автоматическое обновление баланса счета при добавлении/удалении операций,
аналитику (разница доходов/расходов, группировка по категориям), импорт/экспорт данных в CSV, JSON, YAML,
а также ручной пересчет баланса и сбор статистики времени выполнения сценариев.

## Единый code style
В проекте соблюдается единый стиль кодирования:

Используются стандартные соглашения Java (camelCase для методов и переменных, PascalCase для классов).

Отступы – 4 пробела.

Фигурные скобки открываются на той же строке.

Пакеты именуются в соответствии с доменной структурой (com.tigrbank.*).

Для форматирования можно использовать встроенные средства IntelliJ IDEA или плагины (например, Checkstyle).

## Соблюдение принципов SOLID
Каждый принцип проиллюстрирован конкретными классами:

Single Responsibility:

BankAccount, Category, Operation отвечают только за хранение данных.

Репозитории (InMemoryBankAccountRepository) отвечают только за хранение.

Сервисы (AccountService, OperationService) содержат бизнес-логику для своей сущности.

Open/Closed:

Интерфейсы Repository, DataExporter, DataImporter позволяют добавлять новые реализации 
(например, PostgresBankAccountRepository или XmlExporter) без изменения существующего кода.

Liskov Substitution:

Любая реализация Repository<BankAccount> (например, InMemoryBankAccountRepository) может быть заменена другой без изменения клиентского кода.

Interface Segregation:

OperationRepository расширяет базовый интерфейс Repository и добавляет специфичные методы (findByBankAccountId), 
что не заставляет другие репозитории реализовывать ненужные методы.

Dependency Inversion:

Все сервисы зависят от абстракций (интерфейсов репозиториев), а не от конкретных классов. Это достигается через DI-контейнер.

## Взаимодействие модулей через DI-контейнер

Используется самописный DIContainer, который регистрирует зависимости и предоставляет их по запросу.
В классе AppConfig происходит настройка контейнера: репозитории регистрируются как синглтоны, 
сервисы – как transient (создаются при каждом разрешении через supplier). 
Консольное приложение получает все необходимые сервисы через контейнер,
что обеспечивает слабую связанность и упрощает тестирование.

##  Ситуации, при которых появятся проблемы добавления нового функционала или расширения бизнес-логики

Изменение логики обновления баланса. 
Сейчас баланс обновляется при создании/удалении операций.
Если потребуется добавить поддержку валют или комиссий,
придется менять OperationService и, возможно, AccountService. Это может затронуть несколько классов.

Добавление нового формата импорта/экспорта. 
С текущей архитектурой это легко: достаточно реализовать
интерфейсы DataExporter и DataImporter и зарегистрировать их в контейнере. Проблем не возникает.

Добавление нового типа сущности (например, «Бюджет»). Потребуется создать новые классы, репозиторий, 
сервис и модифицировать многие существующие модули (например, импорт/экспорт придется расширять для работы с новой сущностью).
Если бы мы использовали более абстрактное хранение (например, общий репозиторий для всех сущностей), 
расширение было бы проще, но тогда нарушилась бы типобезопасность.

## Аргументы, почему введенные абстракции улучшили качество дизайна
Интерфейсы репозиториев позволили отделить логику хранения от бизнес-логики.
Это упрощает тестирование (можно подменить моками) и даёт возможность легко сменить способ хранения
(например, с in-memory на БД) без изменения сервисов.

Интерфейсы экспорта/импорта позволяют добавлять новые форматы, не трогая существующий код. Это соблюдение принципа Open/Closed.

DI-контейнер централизует создание объектов и управление зависимостями. 
Убирает жёсткие связки new, делает код более гибким и тестируемым.

Разделение на слои (domain, repository, service) чётко определяет ответственность каждого модуля.
Это упрощает понимание и поддержку кода.

## Реализация работы с данными из файлов
Реализован импорт/экспорт в трех форматах: CSV, JSON, YAML.

CSV: ручная запись/чтение с простым парсингом.

JSON: используется библиотека Jackson, сериализация в список объектов.

YAML: используется Jackson.

## Нагрузочное тестирование


1. Запустите  приложение (сервер на порту 4567 должен быть активен).
Так
```bash
# 1. Очистить и собрать проект
mvn clean package

# 2. Запустить приложение из JAR-файла
java -jar target/tigrbank-finance-1.0-SNAPSHOT.jar
```
или так
```bash
mvn exec:java -Dexec.mainClass="com.tigrbank.console.ConsoleApp"
```
лучше первый способ для нагрузочного тестирования.

2. Откройте JMeter → File → Open → выберите этот файл nagrtestsaving\Summary Report.jmx.

3. Запустите тест (зелёная стрелка). Дайте ему поработать не менее 60 секунд.

4. Остановите тест (красный квадрат).

5. Посмотрите результаты на вкладках Aggregate Report или Summary Report.


### Описание пользовательского сценария 

Сценарий имитирует работу пользователя, который:

Создаёт банковский счёт (POST /api/accounts)

Создаёт категорию (POST /api/categories) – например, «Зарплата» (доход)

Создаёт операцию (POST /api/operations) – доход на 5000 руб.

Читает список счетов (GET /api/accounts)

Читает список операций (GET /api/operations)

Удаляет операцию (DELETE /api/operations/{id})

Получает аналитику (GET /api/analytics?start=...&end=...)

Все шаги выполняются последовательно в одном сценарии. В скрипте добавлены случайные задержки sleep() и проверки ответов (статус 200/201/204). Это соответствует требованию комбинированного сценария (GET, POST, DELETE).
